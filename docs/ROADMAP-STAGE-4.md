# نقشه راه پس از مرحله ۴ — اتصال موتور چهره و موتور حضور

مرحله ۴ (دستگاه / PWA / Kiosk) تحویل داده شده و تست شده است. در این مرحله **هیچ موتور واقعی
چهره‌ای ساخته نشده**؛ همه چیزِ مربوط به شناسایی، «قرارداد» است. این سند نشان می‌دهد هر قابلیت
از کجا و بدون بازنویسی به موتور واقعی وصل می‌شود.

> **دو قاعده تغییرناپذیر:** ۱) تشخیص Liveness هرگز پیاده‌سازی نمی‌شود (نه کد، نه ستون).
> ۲) تا اتصال موتور واقعی، هیچ‌جا ادعا نمی‌شود که شناسایی چهره کار می‌کند.

## ۱) موتور تشخیص چهره (مرحله ۵)

| موضوع | وضعیت فعلی (ساختار آماده) |
|---|---|
| قرارداد موتور | `GET /api/v1/device/engine` → `face_engine: unavailable`, `stage: 5`, `liveness: not_used`, `requires_request_id: true` |
| درخواست شناسایی | `POST /api/v1/device/recognition` با `request_id` اجباری و idempotency روی `attendance_device_requests (UNIQUE device_id+request_key)` |
| پاسخ آماده موتور | `DeviceService::engineResponse()` — نگاشت کد موتور به متن دقیق فارسی و پاکت استاندارد |
| کدهای نتیجه | `recognized` / `no_face` / `multiple_faces` / `unknown_face` / `employee_inactive` |
| تصاویر نمونه | `attendance_employee_faces` با `sample_index` ۱..۳ (ثبت ۳ نمونه = مرحله ۵) |
| وضعیت ثبت چهره | `attendance_employees.face_status` = `not_enrolled` / `partial` / `complete` |
| Embedding | **وجود ندارد**؛ در مرحله ۵ یک ستون/جدول برداری باید طراحی شود (فعلاً هیچ ستونی برای آن ساخته نشده) |
| مدل | **هیچ مدلی در پروژه نیست** (نه TensorFlow.js، نه face-api.js، نه فایل وزن) |
| Liveness | **نخواهد آمد** — نه کد، نه ستون، نه گزینه |

نقطه اتصال در مرحله ۵: `DeviceKioskController::recognition()` → به‌جای پاسخ
`503 FACE_ENGINE_UNAVAILABLE`، فراخوانی سرویس موتور و سپس `DeviceService::engineResponse()`.
رابط کاربری، حالت‌های دوربین، صفحه موفقیت/خطا و متن‌های فارسی **همین حالا آماده‌اند** و تغییری لازم ندارند.

## ۲) موتور ثبت حضور (مرحله ۶)

| موضوع | وضعیت فعلی (ساختار آماده) |
|---|---|
| قرارداد ثبت | `POST /api/v1/device/attendance` — بررسی مستأجر، `Employee::canAttend()`، شعبه، سپس `503 ATTENDANCE_ENGINE_NOT_READY` |
| جدول رکوردها | `attendance_records` با `UNIQUE (employee_id, work_date)` + ستون‌های ورود/خروج/دقیقه کار/تأخیر/اضافه‌کار/وضعیت (از مرحله ۳) |
| جلوگیری از ثبت دوباره | `attendance_device_requests` (idempotency در سطح دیتابیس) + گارد سمت کلاینت فقط برای UX |
| شیفت و محاسبه | `Shift::timeMinutes()`, `Shift::workMinutes()`, پشتیبانی شیفت شبانه (`crosses_midnight`) |
| صف آفلاین | ساختار و UI آماده است (شمارنده صف، بنر آفلاین، وضعیت اتصال)؛ **بازپخش تصمیم مرحله ۶ است** |
| سیاست «چه چیزی آفلاین ثبت شود» | تصمیم‌گیری نشده — نیازمند طراحی امنیتی (بدون ذخیره‌سازی حساس روی دستگاه) |

## ۳) کارهای تعویق‌افتاده دیگر

| مورد | مرحله |
|---|---|
| Excel (خروجی گزارش‌ها) | بعد |
| ربات تلگرام (رویدادهای ورود/خروج) | بعد |
| موتور حقوق و دستمزد (محاسبه نهایی) | بعد |
| شیفت‌بندی چندگانه/هفتگی | بعد (ساختار `employee_shifts` آماده است) |

## ۴) قواعدی که در همه مراحل بعدی باید حفظ شوند

1. همه جداول فقط `attendance_*` — هیچ تماسی با `barber_*`, `cafe_*`, `clinic_*`, `zibaei_*`,
   `sarmadpf_*` (`Database::table()` + `SqlGuard`).
2. توکن دستگاه **فقط** در هدر `Authorization`؛ هش در DB؛ بدون توکن معتبر هیچ داده کارمند/حضور
   برنمی‌گردد و `customer_id`/`branch_id` هرگز از بدنه درخواست خوانده نمی‌شود.
3. کد فعال‌سازی یک‌بارمصرف و زمان‌دار است؛ در DB فقط هش + پیشوند ۴ کاراکتری.
4. کارهای مالک‌محور (کد فعال‌سازی، بازنشانی/چرخش/لغو/حذف دستگاه، تغییر شعبه دستگاه،
   سوئیچ‌های امنیتی) هرگز به پنل مدیر اضافه نشوند — مدیر فقط مشاهده‌ی دستگاه‌های مشتری خودش.
5. هر رخداد جدید در واژگان `AuditService`/`DeviceLog` یک کلید داشته باشد (نه رشته آزاد).
6. Liveness هرگز؛ و تا اتصال موتور، «قرارداد» هرگز به‌عنوان «قابلیت آماده» معرفی نشود.
